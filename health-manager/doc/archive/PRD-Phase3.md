# Health Manager — Phase 3：OCR 识别（占位）

Phase 1 跑通基础指标，Phase 2 加了图片归档 + 病历 + 化验数据。Phase 2 的化验单照片是"死照片"——存着但没法自动分析。Phase 3 把 OCR 加上，照片里的数字能被自动读出来、校对、导入数据库。

> 本文件是占位 PRD，只写已经想清楚的方向，细节留白。等 Phase 2 落地后再细化。

## 阶段目标

让化验单照片从"死照片"变成"活数据"。用户上传一张化验单，系统自动识别出指标，Agent 校对，用户确认后导入——全程不用手动念数字。

## 化验单三步分离（完整形态）

Phase 1/2 只有第一步，Phase 3 补齐后两步：

**第一步·上传**（Phase 2 已有）：用户上传化验单图片，按检查日期归档。状态标记为**待识别**。

**第二步·识别**（Phase 3 新增）：对已归档的图跑 OCR，把图片变成结构化数据。图片状态变成**已识别**。用户在界面上能看到这张图识别出了哪些指标、各项的值。

**第三步·导入**（Phase 3 新增）：用户查看识别结果，确认无误后导入数据库。图片状态变成**已导入**，指标浏览器里出现新数据。

状态流转：`待识别 → 已识别 → 已导入`。三步独立，用户能在任何一步停下。

## OCR 架构方向

已确定的设计方向：

### 按需子进程

- App 主进程常驻（平台机制），永远不 import torch，始终轻量
- 需要识别时 spawn 独立子进程跑 OCR（沿用现有 process_ocr.py 的逻辑）
- 子进程加载模型、识别、输出结果、退出，内存立即释放
- 平时 App 只占几十 MB，只有识别那几十秒才多出一个 GB 级子进程

### OCR 开关

- App 界面有开关，默认关闭
- 开启时检查 torch 和 GLM-OCR 模型文件是否就绪，没装则引导下载
- 关闭时回到 Phase 2 的纯存档模式，已下载依赖保留不删
- 开关状态持久化到 SQLite 的 settings 表

### 阶段式进度

模型加载拿不到精确百分比，用阶段式进度加文字状态：启动引擎 → 加载 torch → 加载模型 → 识别中 → 完成。子进程往 stdout 输出阶段标记，主进程读后通过 WebSocket 推给前端。

## 识别与校对解耦

- **识别在后端**（图片到不了 Agent，Agent 看不到图）
- **校对导入在 Agent**（这是大语言模型的强项，且只操作文本，不依赖多模态）

这样即使接的 Agent 模型不支持多模态，也能完成校对录入——它拿到的是识别后的文本数据，不是图。

## Notification

Phase 3 开始需要 Notification。OCR 识别完成后通知 Agent 来校对导入：

- 识别成功：`用户上传的化验单已识别完成。请调用 get_pending_upload 获取识别数据，校对后用 record_lab_result 录入`
- 识别失败：`用户上传的化验单识别失败，请引导用户口述关键指标`

Notification 的 content 字段只能传文本字符串（平台强制校验），结构化数据由 Agent 调 `get_pending_upload` 工具主动拉取。
