# Health Manager — 架构总览

> 本文件是整个产品的顶层设计：定位、模块划分、跨模块共享的原则。
> 每个模块的细节在各自的《模块-X》文档里。

## 产品定位

Health Manager 是一个**个人身体管理的统一入口**——在一个地方管好身体相关的所有事。
用户和 Agent 对话录入数据，App 把数据展示成趋势和摘要。

不做什么：不给医疗诊断、不替用户做健康决策。Agent 只负责记数据和描述已记录数据里的规律。

## 模块划分

App 底部四个 tab，从左到右：

| 模块 | 定位 | 文档 |
|---|---|---|
| 摘要 | 全貌入口：基础身体数据 + 其他模块的要点 | 本文档「摘要页」一节 |
| 饮食 | 每日吃了什么 + 卡路里 + 营养素 + 目标 | 模块-饮食 |
| 健身 | 能力进步（主线）+ 运动日记 | 模块-健身 |
| 疾病 | 化验 / 病历 / 化验单图片 / OCR | 模块-疾病（待写） |

## 工具总览

按实体聚合，共 14 个工具（`agentId` / `sessionId` 由平台自动注入，Agent 不填）。每类数据的增删查改规则见「共享原则 > MCP 工具」。

| 模块 | 工具 | 用途 |
|---|---|---|
| 体征 | get_body_metrics | 查最近体征（体重/血压/心率）+ 身高/称呼 |
| 体征 | update_body_metrics | 记或改体征，部分更新，传过去日期可改历史 |
| 健身 | record_strength | 记能力成绩，返回比上次变化 |
| 健身 | record_workout | 记运动日记，含卡路里消耗 |
| 健身 | get_strength_history | 查某动作能力历史 |
| 健身 | get_workout_diary | 查运动日记，每条带 [编号] |
| 健身 | update_workout | 按编号改一条运动记录（patch，只动传入字段） |
| 健身 | delete_workout | 按编号删一条运动记录 |
| 饮食 | record_diet | 记一条饮食，三大宏量必填 |
| 饮食 | get_diet_log | 查某天饮食，每条带 [编号] |
| 饮食 | update_diet | 按编号改一条（patch，只动传入字段） |
| 饮食 | delete_diet | 按编号删一条 |
| 饮食目标 | set_diet_goals | 设卡路里/宏量目标，部分更新，三个宏量需同时给 |
| 饮食目标 | get_diet_goals | 查目标（含自动/手动模式） |

## 摘要页

摘要页是打开 App 第一眼。分两块：**顶部固定区** + **下方动态卡片区**。
卡片显示各模块各项的最新状态，点进去看该项目的详情和历史。

完整数据随时能去对应模块的 tab 看——摘要只是"今天的看点"，不是全量罗列。

### 顶部固定区（写死）

- **日期**（X月X日 星期X）
- **用户名字**
- **一句话状态**：由规则引擎从今天的数据里挑最值得说的一句（见下），没有特别的就显示中性问候。

一句话状态的生成（取当天最突出的一条）：

- 有异常 → "今天血压偏高，留意一下"
- 创新高 → "深蹲创新高 100kg"
- 大变化 → "体重比上周轻了 2kg"
- 都没有 → "今天数据平稳"（或按时段问候）

### 动态卡片区（最多 6 张，规则挑选）

挑选规则是**写死的、确定的**——同样的数据永远选出同样的卡片，只是会跟着每天的数据变化而变。
每张卡都带一个小标签说明"为什么出现"，所以永远不会显得莫名其妙。

每张候选卡按下面规则打分排序：

**值得注意（最优先）**

- 血压 收缩 ≥140 或 舒张 ≥90 → 标"需关注"
- 化验有异常标记 → 置顶，标"异常"

**变化较大**

- 体重 7 天内变化 >3kg → 标"变化较大"
- 血压比上次变化 >10 → 标"变化较大"
- 能力创新高（新 PR）→ 标"进步"

**最近更新**

- 今天/昨天有记录的卡加分

**排序**：值得注意 > 变化较大 > 最近更新，取前 6 张。
**兜底**：一条突出的都没有 → 显示默认几张（体重 / 血压 / BMI），保证页面不空。

### 基础身体数据

身高 / 体重 / 血压 / 心率这些基础体征不单独开 tab，通过摘要页的卡片进入详情。
身高是静态属性，在摘要页表单填，不走对话。
体征支持改历史：update_body_metrics 传过去某天的日期，即修改那天的体重/血压记录。

## 共享原则

### 录入通道

- **对话口述为主**：动态数据（体重、血压、饮食、运动、能力成绩）都走 Agent 对话录入。
- **表单只管静态属性**：如身高。其余一律对话。

### 数据存储

- 单一 SQLite 文件（`data/health.db`），按模块分表。
- Schema 版本管理（PRAGMA user_version），加表即升版本，自动迁移。

### MCP 工具

- 记录类工具，记完返回「本次 + 上次 + 变化量」（链式对比），让 Agent 直接给反馈，不另查。
- 查询类工具，让 Agent 想看历史时拿得到。
- 每条数据都支持增删查改：不只录入，已记下的能改、能删（饮食按编号、体征按日期）。
- 查询工具返回完整对象，列表类带每条记录的 id，Agent 拿到就能直接改/删，不用再调一次「获取详情」。
- 工具按实体聚合减量：体征、目标这类「设值型」用部分更新合并成一个写入工具；饮食这类「列表型」数据增删查改各一个独立工具。
- `agentId` / `sessionId` 由平台自动注入，Agent 不填。

### 校对分层

- **硬规则**（下沉到工具内部）：防离谱值的兜底范围，工具直接拒绝。
- **软校对**（Agent 提示词层）：异常波动提醒，由 Agent 判断。

### 通知设计

数据从对话单向流入的模块（体征、饮食、健身）不需要 App 主动通知 Agent。用户在界面上做的操作也都不回头通知 Agent——Agent 需要最新值时自己调查询工具拿。

| 触发场景 | 是否通知 Agent | 说明 |
|---|---|---|
| 设身高 / 设称呼（界面表单） | 否 | 静态属性，Agent 用时查 get_body_metrics |
| 设卡路里目标 / 宏量目标 / 切目标模式（设置页） | 否 | Agent 用时查 get_diet_goals 拿最新 |
| 切换演示数据 | 否 | 仅影响前端展示，不进对话 |
| 后台异步任务（如未来的化验单 OCR） | 是（未来） | 完成后通知 Agent 来校对，当前模块无此场景 |

疾病模块的 OCR 识别完成才需要 Notification，待疾病模块细化。

### Agent 行为

- 工具负责**给数据**（当前值 + 历史），怎么用、要不要对比、要不要说，由 Agent 自己判断。
- 单向流入的模块（基础、饮食、健身），用户喂数据的**唯一通道是和 Agent 聊天**——没有表单录动态数据、没有 App 反向通知。
- Agent 调工具时，缺的参数可以用语言模型自己的常识填（例如饮食的卡路里、营养素，用户没报时 Agent 自行估算）——前提是工具描述里授权了它能这么干。
- 不在产品里规定 Agent 的人格或话术。

## 技术架构

复用已跑通的双通道：

- **stdio MCP**：暴露各模块工具给 Agent。
- **uvicorn HTTP**：serve 前端静态文件 + WebSocket。
- **单进程双通道**：anyio task group 同时跑 MCP 和 HTTP，共享同一个 SQLite。
  Agent 调工具写库后，同一进程内通过 WebSocket 推送给前端。

数据流：

```
用户对话 → Agent 调 MCP 工具 → 工具写 SQLite + 返回对比值给 Agent
                              → WebSocket 推送 → 前端刷新
```

WebSocket 快照按模块命名空间：`{ basics, diet, fitness, disease }`，
加模块只加对应命名空间，其他模块代码不动。

前端：React + Vite 多入口（桌面 / 移动），复用现有基建。
